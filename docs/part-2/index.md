# 第二部分：从模型行动到最小 Agent

第一部分结束时，城市旅行助手已经拥有模型、上下文和工具。模型能够理解用户的旅行需求，程序也能够执行天气查询、景点信息查询和费用计算，但工具调用仍由开发者手动指定。

要让模型参与行动选择，程序不能再把工具选择写死成固定条件，而要看懂模型下一步要做什么。由于模型输出来自外部，既可能遵循约定，也可能出现非法 JSON、错误字段、不存在的工具或不合适参数。程序不能因为一段输出看起来合理，就直接让它进入真实执行。

这一部分建立模型输出与程序执行之间的完整边界。模型负责提出行动请求，程序负责解析、校验和执行；工具产生结果后，程序再把结果组织成 Observation 返回模型。模型拥有语义上的选择权，程序始终保留真实执行权。

整个构造过程分为四步：

```text
自然语言任务
→ 结构化 Action
→ Parser 与 Validation
→ Tool Result 转换为 Observation
→ Agent Loop 持续运行
```

第五章先规定 Action Protocol，让模型不再直接生成任意回答，而是输出工具名称、参数或 `finish`。这份输出仍是字符串，不等于“动作已被执行”。

第六章建立 Parser。它把不可信的模型文本转换为 Python 数据，检查字段、行动名称和参数结构，只有通过校验的输出才能成为 `AgentAction`。

第七章执行一次已经通过校验的 Action，并把 Tool Result 与工具名称、参数和执行状态组合成 Observation。只有 Observation 被加入下一次模型请求，工具结果才会真正影响模型回答。

第八章把这些组件连接成 Agent Loop。每轮模型都可以继续选择工具，也可以通过 `finish` 结束任务；程序则负责限制步数、更新上下文并决定循环何时停止。

| 章节 | 主要问题 | 本章建立的能力 |
|---|---|---|

阅读这一部分时，需要关注每项数据经过了哪一道边界。模型原始输出不是 `AgentAction`，`AgentAction` 也不是 Tool Result；Tool Result 只有被组织成 Observation 并重新发送给模型，才会成为下一轮决策依据。

第二部分结束时，城市旅行助手已经能够围绕用户目标连续选择工具、接收反馈并在任务完成时结束。这是全书第一个完整的工具型 LLM Agent。
