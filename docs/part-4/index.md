# 第四部分：从可运行到可维护系统

第八章已经证明城市旅行助手可以连续调用工具，第九至十一章又展示了不同的执行与结果改进方式。只要模型按要求输出、工具正常返回并最终生成 `finish`，程序就能够完成一项旅行任务。

但是，能运行不等于可靠。

一次成功演示只能说明某一次输入、某一次模型输出和某一次工具执行恰好顺利完成。它不能说明网络失败时程序会怎样恢复，模型持续输出非法格式时是否会停止，也不能证明一次重构没有破坏已有行为。程序若只留下最终回答，我们甚至无法确认它实际调用过哪些工具。

可靠的 Agent 需要建立一组可以被程序检查的边界：错误发生在哪里，哪些操作允许重试，最终为什么终止，运行到了什么状态，执行过程留下了哪些轨迹，以及修改代码后怎样重复验证原有行为。随着代码逐渐稳定，还需要明确模块职责和依赖方向，使同一项能力不再散落在多个脚本中。

这一部分会依次处理五个关键问题。

第十二章区分不同层级的失败，并为网络请求、模型格式、工具执行和重新决策建立有限重试。无论成功还是失败，程序都会返回明确的 `AgentRunResult` 和 `TerminationReason`。

第十三章保存 `AgentState`、模型 Attempt、StepRecord 和 Execution Trace。最终结果说明程序怎样结束，状态说明当前运行到哪里，轨迹则说明程序怎样到达这个结果。日志用于传播运行事件，但不替代结构化轨迹。

第十四章使用 Mock LLM 把模型输出变成可控测试输入。Parser、工具、Controller、状态隔离和失败路径由此能够在没有网络和 API Key 的环境中重复验证，并产生基础 Metrics。

第十五章在测试保护下进行重构。各章代码继续保存教学演化快照，已经稳定的公共职责则进入 `simple_agent` 包。Package、Module Boundary、Dependency Direction 和 Public API 使代码从“每章都能运行”走向“公共实现可以维护和复用”。

第十六章使用最终包重新构建完整旅行助手。应用提供模拟数据、旅行工具和 Prompt，公共包负责 Agent Loop、重试、状态与轨迹；Agent 正常结束后，应用再从执行结果中整理 Evidence，并使用 Reflection 检查最终答案。

阅读这一部分时，需要把“可靠”理解为多个层次共同成立，而不是把所有异常都交给重试。明确拒绝非法输入、在达到上限时停止、保存真实执行轨迹，以及用测试防止行为回退，都属于可靠性的一部分。模块边界同样重要，因为无法维护的代码很难长期保持这些行为。
