# 前言

## 从一次模型调用开始

第一次在 Python 中调用大语言模型通常并不困难。只要准备好接口配置、组织好消息，再从响应里取回生成文本，一个最小的语言模型应用就能运行起来。模型可以回答问题、解释概念、生成代码，也能把许多过去需要规则硬编码的场景变成自然语言处理。

真正的困惑往往从这之后开始。

模型可以说“我需要查询天气”，但这句话本身不会真正访问天气服务；程序可以执行一个函数，但返回值也不会自动进入模型上下文；模型可能连续提出行动，却未必知道该在何处停止。只要任务开始涉及实时信息、外部工具、多步执行和环境反馈，单次文本生成就不够用了。我们需要让模型的判断进入程序决策，让程序执行结果再回到模型，并由清晰的控制结构推动流程。

从一次模型调用到一个能够完成任务的智能体，中间还隔着一组不能被省略的结构：消息如何组织、工具如何开放、模型如何提出行动、程序如何解析与校验行动、工具结果如何转为新的观察、状态如何保存、循环如何继续，以及失败发生后程序为什么应当重试或停止。

这些结构并不神秘。它们最终都体现在普通的数据、函数、条件和循环里。只是当成熟框架把能力封装成统一接口后，学习者往往只能看到“调用 Agent”这一行，却很难继续追问：这一行代码内部到底发生了什么？

## 为什么还要自己实现 Agent

今天已经有许多成熟的智能体框架、开发平台和工具链。它们能够帮助开发者快速接入模型、注册工具、构建工作流、保存状态，甚至组织多个智能体共同完成任务。对于需要尽快交付应用的人来说，这些框架十分有价值。

但“能够使用框架”和“理解智能体”并不是同一件事。

当一个工具调用失败时，是工具执行器决定重试，还是模型重新选择行动？当模型输出一段带有 Markdown 标记的 JSON 时，程序应该直接修正、要求模型重写，还是终止当前任务？当一个 Agent 连续三次调用同一个工具时，这究竟是必要重试，还是已经陷入循环？当最终答案遗漏了已经获得的信息时，问题出在工具、计划、执行，还是答案生成阶段？

这些问题无法只靠记住某个框架的 API 来回答。它们要求我们看见模型与程序之间的边界，看见一次行动怎样从文本变成真实操作，也看见程序怎样在不完全信任模型的前提下继续运行。

因此，本书不会从一个已经完成的 Agent 框架讲起。我们不会先展示一组基类、注册器、适配器和抽象接口，再要求读者反向推测它们为什么存在。相反，我们会从一个最小程序开始，让每一个结构在问题真正出现时再进入系统。

当程序只能完成一次模型调用时，我们引入消息和上下文；当模型只能生成文本时，我们引入工具与行动协议；当模型输出还不能被程序信任时，我们引入解析与校验；当工具结果无法影响后续判断时，我们引入 Observation；当固定调用次数无法处理多步任务时，我们建立 Agent Loop；当程序开始出现错误、重复行动和无法结束的问题时，我们再讨论重试、终止、状态、轨迹和测试。

抽象并不是先于问题提前设计出来的。它应当来自真实问题，并在职责反复出现后自然稳定。全书最后形成的 `simple_agent` 包，不是学习过程的起点，而是这个过程自然留下的结果。

## 把智能体一层层构造出来

这本书围绕一个问题展开：

> 怎样从一次普通的大语言模型调用，逐步构造出一个能够使用工具、接收反馈并持续完成任务的智能体？

为回答这个问题，我们会沿着一条连续的构造路径前进：

```text
LLM → Message → Context → Tool → Action → Parser
→ Observation → Agent Loop → Reliability → State → Test → Package
```

这条路径并不是一份概念清单。每一个新组件都要解决前一版本中已经出现的具体缺陷。

最初，模型只能根据一条消息生成回答。加入上下文后，它能够理解连续对话，但仍然只能处理当前消息中已有的信息。工具让程序第一次拥有外部执行能力，但工具仍由开发者手动选择。Action 让模型能够提出结构化行动，Parser 再将不可信的模型文本转换成程序认可的数据。Observation 把工具结果送回模型，而 Agent Loop 则让这种“判断—行动—反馈”的过程持续运行，直到任务完成或程序强制停止。

在此基础上，我们会分别观察几种常见控制方式。ReAct 关注获得新反馈之后的下一步行动；Plan-and-Solve 关注执行之前如何形成完整计划；Reflection 则关注候选结果是否真正满足任务，以及怎样根据证据进行修订。它们并不是从低级到高级的三层升级，而是处理不同阶段问题的三种方法。

能够运行的 Agent 仍然不等于可靠的 Agent。模型可能输出非法格式，工具可能返回业务错误，网络请求可能暂时失败，程序可能重复执行相同行动，也可能始终得不到 `finish`。因此，后半部分会把注意力从“怎样完成任务”转向“怎样知道系统发生了什么，以及怎样证明修改真的有效”。我们会建立失败分类、有限重试、终止原因、状态、执行轨迹、日志、Mock LLM 和自动化测试，最后再把稳定职责提取成可复用包。

这本书不会隐藏失败过程。示例中的模型不一定每次都按照预期输出，程序也不会因为模型生成了一段看起来合理的文本就直接相信它。很多时候，真正值得理解的并不是一次成功运行，而是某个组件被删除、输出被破坏或工具执行失败后，系统为什么会在特定位置停止。

## 一个持续生长的旅行助手

从第二章开始，我们会持续修改同一个城市旅行助手。

最初，它只能回答一个一般性的旅行问题；随后，它开始保存对话，理解“它”“继续解释”和“刚才提到的景点”这类依赖历史的表达。接着，我们会为它加入本地模拟天气、景点信息和费用计算工具，让程序拥有模型知识之外的执行能力。

之后，旅行助手不再只生成自然语言回答，而是开始输出结构化 Action。程序将检查这些 Action 是否符合协议，再决定是否执行。工具返回的结果会被组织成 Observation，进入下一轮上下文。等到 Agent Loop 建立后，同一个旅行任务可以连续经历天气查询、景点查询、费用计算和最终回答，而工具调用顺序不再由开发者提前写死。

后续章节仍然围绕这个助手展开。我们会观察它如何在 ReAct 中根据每次 Observation 调整行动，如何在 Plan-and-Solve 中先形成计划，如何在 Reflection 中检查答案是否遗漏证据或违反用户约束。最后，我们会让它能够报告明确的失败原因、保存完整运行轨迹、接受确定性的自动化测试，并使用最终形成的 `simple_agent` 包重新完成整项任务。

主线中的天气、景点、票价和开放状态均来自本地模拟数据。这样做并不是为了回避真实系统，而是为了让每次运行都可以被理解、复现和测试。我们关注的是 Agent 如何组织信息与行动，而不是某个外部服务在某一天返回了什么。

同一个程序持续生长，也意味着读者不需要在每一章重新认识一个陌生案例。前一章留下的问题，会成为下一章真正的起点；前一章已经建立的代码，会继续参与下一步构造。到全书结束时，我们看到的不会是十几个彼此独立的 Demo，而是一个系统从简单调用逐步演化为可运行、可观察、可测试程序的完整过程。

## 写在阅读之前

这本书更适合被“运行”，而不只是被阅读。

在执行每一章代码之前，可以先预测程序会怎样工作：模型能够看到哪些消息？当前输出还是普通文本，还是已经变成 Action？哪一段代码拥有真正的执行权？工具结果是否已经进入下一轮上下文？程序在什么条件下会继续，又会在什么条件下停止？

运行成功案例之后，也请主动制造错误。删掉一条历史消息，改变工具参数名称，让模型输出不完整的 JSON，不把 Observation 返回模型，或者暂时移除最大步数。观察程序在哪一层失败，再回头判断当前章节引入的组件究竟保护了什么。

不必机械记住所有代码。更重要的是，在完成一章后能够不用查看正文，回答几个简单的问题：这一章新增了什么结构？它接收谁的输出，又把结果交给谁？如果删除它，系统会出现什么问题？它为什么应该由程序负责，而不是完全交给模型？

正文只展示当前需要理解的关键代码，完整版本放在对应的代码目录中。部分章节依赖真实大语言模型，因此不同模型、不同服务或不同运行次数可能产生不同输出。示例轨迹不是唯一正确轨迹，模型偶尔不遵守格式也不意味着学习过程失效。相反，这些不确定性正是 Agent 工程需要处理的现实条件。

本书主动收窄了范围。它不会系统讲解某个成熟框架，也不会在主线中展开长期记忆、完整 RAG、多智能体协作、通信协议或模型训练。并不是因为这些技术不重要，而是因为在理解最小 Agent 的边界之前，过早引入它们只会增加新的封装层。当我们能够亲手实现模型调用、工具选择、行动解析、环境反馈、状态管理和 Agent Loop 后，再进入更复杂的系统，会更容易理解那些框架究竟替我们完成了什么。

Simple Agent 的形成受到 Datawhale Hello-Agents 项目的启发。Hello-Agents 提供了覆盖智能体基础、经典范式、框架、记忆、检索、通信、训练和综合案例的系统性学习资料。本书选择了一条更窄的路径，只专注于“一个最小 Agent 怎样从零构造出来”。Simple Agent 不是 Hello-Agents 的官方精简版本，也不是对其代码的二次封装，而是一份围绕这一问题独立组织和实现的学习记录。

希望读完这本书之后，你得到的不只是一个能够运行的 Agent，也不只是一个可以继续扩展的 Python 包。更重要的是，当你再次看到一个成熟框架中的 Agent、Tool、State、Graph 或 Executor 时，能够知道这些名称背后对应的程序职责，能够判断哪些部分可以交给模型，哪些边界必须由代码控制，也能够在系统失败时知道应该从哪里开始检查。
